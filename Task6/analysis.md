# Отчёт по результатам анализа Kubernetes Audit Log
    
## Подозрительные события

1. Доступ к секретам:
    - Кто: minikube-user с параметром --as=system:serviceaccount:secure-ops:monitoring.
    - Где: в неймспейсе kube-system
    - Почему подозрительно: ServiceAccount из неймспейса приложений secure-ops пытается читать секреты в системном `kube-system`. Запрос отклонён по 403, но сама попытка подозрительна. 

2. Привилегированные поды:
    - Кто: minikube-user в неймспейсе secure-ops, имя пода privileged-pod.
    - Комментарий: pod создан с privileged: true, это даёт контейнеру права root на ноде. Запрос прошёл успешно по 201, значит в кластере нет политик, запрещающих создание привилегированных подов.

3. Использование kubectl exec в чужом поде:
    - Кто: minikube-user.
    - Что делал: exec в pod coredns-7d764666f9-dvrks в неймспейсе kube-system, выполнил команду cat /etc/resolv.conf. Запрос принят по 101, сама команда внутри coredns не выполнилась, потому что в образе нет утилиты cat. Но факт обращения к чужому поду в системном неймспейсе зафиксирован.

4. Создание RoleBinding с правами cluster-admin:
    - Кто: попытка от minikube-user. RoleBinding escalate-binding должен был дать ServiceAccount monitoring права cluster-admin.
    - К чему привело: в audit.log событие отсутствует, команда kubectl apply упала при запуске скрипта из-за ошибки в YAML до отправки запроса. Если бы ошибки не было, то юзер получил бы полные права на кластер.

5. Удаление audit-policy.yaml:
    - Кто: minikube-user через параметр --as=admin командой kubectl delete -f /etc/kubernetes/audit-policy.yaml.
    - Возможные последствия: в audit.log событие отсутствует, команда упала в скрипте (файла по такому пути на хосте нет). Плюс удалить его через API нельзя — это конфигурационный файл kube-apiserver на ноде. Если бы атакующий получил доступ к ноде и удалил файл, аудит перестал бы вестись и все последующие действия не были бы записаны.

## Вывод

Симуляция показала, что
- Есть защита от чтения чужих секретов
- Нет защиты от создания privileged пода. Если учетка с правами создания подов утечет, то хакер получит доступ ко всей ноде
- Нет защиты от kubectl exec. Необходимо ограничить только для ограниченого круга лиц
- Можно представиться admin'ом через --as
- Нужно перепроверить что audit.log нельзя будет выключить или потерять. Сейчас он пишется внутрь apiserver и при рестарте теряется
- Нужно проверить возможность привязки к роли cluster-admin и защититься от этого, если это возможно
